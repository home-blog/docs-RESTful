# cream-coral-pptx

주제나 파일을 받아 **같은 디자인의 발표 덱**을 만듭니다. 디자인은 엔진(`scripts/build_deck.js`)에 들어 있으므로, 할 일은 **내용을 잘 고르고 덱 스펙(JSON)을 쓰는 것**입니다.

결과물:
- `.pptx` — 슬라이드 마스터(표지 · 섹션 · 본문 · 마무리), 섹션, 모든 슬라이드의 발표자 노트, 테마 색 · 한글 테마 글꼴, 네이티브 차트
- `-대본.md` — 시간 배분 표, 슬라이드별 대사, 예비 슬라이드, 질문 대비, 발표 전 체크

## 작업 순서

### 1. 재료와 조건 모으기

사용자가 준 파일을 먼저 끝까지 읽습니다. 그다음 아래가 정해졌는지 확인하고, 빠진 것만 짧게 묻습니다. 대화나 파일에 이미 있으면 묻지 않습니다.

- **주제와 핵심 메시지** 한 줄
- **청중** — 수준에 따라 무엇을 생략할지가 바뀝니다. "기초는 아는 동료"라면 정의보다 설계 의도와 트레이드오프를 보여 줍니다.
- **발표 시간** — 본 슬라이드 수의 기준. 대사 기준으로 1분에 약 1.5~2장.
- **꼭 넣을 항목, 날짜 · 발표자**

### 2. 개요 짜기 (한 장에 메시지 하나)

- 제목은 주제어가 아니라 **그 슬라이드가 말하는 한 문장**으로 씁니다. ("상태 코드" ✗ → "200에 실패를 담으면 생기는 일" ○)
- 3~5장마다 `section` 슬라이드로 끊고, 마지막은 `closing`으로 정리합니다.
- 시간 안에 못 넣는 내용, 질문이 나올 만한 내용은 버리지 말고 **`spare`(예비 슬라이드, 맨 뒤)** 로 보냅니다.
- 같은 설명은 한 번만 자세히 하고, 뒤에서는 "앞에서 본 …"으로 받습니다.

### 3. 화면 재료 고르기 — 그린 그림보다 실제 결과물

이 디자인이 가장 신경 쓰는 부분입니다. 아이콘 · 화살표 · 상자를 늘어놓은 인포그래픽은 한눈에 "AI가 그린 그림"으로 보이고 발표의 신뢰를 깎습니다. 대신 **실제로 존재하는 것**을 보여 줍니다.

| 보여 줄 것 | 블록 |
|---|---|
| API 요청 · 응답 | 실제로 `curl -i`를 돌려 저장한 파일 → `http` |
| 코드 | 실제 코드 몇 줄 → `code` (핵심 줄만 `amber` · `coralText`로) |
| 비교 · 규칙 목록 | `table` 또는 `cards` |
| 숫자 | 직접 측정하거나 사용자 데이터 → `chart` (네이티브, 편집 가능) |
| 문서 · 도구 화면 | 실제 스크린숏 → `image` (긴 화면은 `cuts`로 두 칸) |
| 한 문장 결론 | `callout` (덱 전체에서 아껴 씀) |

정직함 규칙:
- **차트 숫자를 지어내지 않습니다.** 측정할 수 있으면 측정 스크립트를 만들어 돌리고(조건 · 반복 횟수 · 중앙값을 노트에 적음), 아니면 사용자 데이터를 씁니다. 둘 다 없으면 차트 제목이나 `badge`에 **"예시"** 를 붙입니다.
- 실제 화면이 아니라 재구성한 화면(문서를 보고 다시 그린 Swagger 등)은 그렇다고 표시합니다.
- 인용 · 표준 번호 · 버전은 확인한 것만 씁니다.

### 4. 대사(notes) 쓰기

모든 슬라이드에 `notes`를 씁니다. 엔진이 이를 발표자 노트와 대본 양쪽에 넣고, 길이로 시간을 어림합니다.
- 말하는 문장으로 씁니다. 화면에 있는 글을 그대로 읽는 대사는 피합니다.
- **듣고 바로 이해되게 쉽게 씁니다.** 대사는 읽는 글이 아니라 한 번 듣고 지나가는 말이라서, 문서 문장처럼 압축하면 어렵게 들립니다.
  - 한 문장에 한 가지만. 쉼표로 이유 · 예외 · 결론을 한 문장에 몰아넣지 않습니다.
  - 용어는 처음 나올 때 바로 풀어 줍니다. ("멱등입니다. 같은 요청을 여러 번 보내도 결과가 같다는 뜻입니다.")
  - 규칙보다 구체적인 예를 먼저, 그다음 "그래서"로 규칙을 말합니다.
  - "첫째 · 둘째", "문제는", "그래서", "정리하면"처럼 말의 길잡이를 넣습니다.
  - 전문 약어(APM, 프리페치 등)와 도구 이름 나열은 줄이고, 화면 표에 이미 있는 내용은 대사에서 빼거나 한 번만 짚습니다.
  - 쉽게 쓰면 길어지기 쉽습니다. 시간이 넘치면 말투를 다시 어렵게 줄이지 말고, 덜 중요한 항목을 빼서 질문 대비(`qa`)나 예비 슬라이드로 보냅니다.
- 사용자가 원하지 않으면 **비유 없이** 실제 동작으로 설명합니다. 퀴즈 · 청중 질문도 요청이 있을 때만.
- 대본 합계가 발표 시간의 85~95%가 되게 맞춥니다(실제로 말하면 늘어남).
- 클릭 애니메이션을 넣은 슬라이드는 대사 안 클릭할 자리에 `[클릭: 무엇]`을 넣습니다. 발표자가 넘길 때를 놓치지 않게 하려는 것이고, 엔진이 개수를 애니메이션과 맞춰 봅니다 (`references/spec-format.md` 6장).

### 5. 덱 스펙 쓰기

`references/spec-format.md`를 읽고 JSON을 씁니다. `assets/example-spec.json`이 모든 슬라이드 종류와 주요 블록을 쓰는 작은 예시입니다. 작업 폴더(사용자 폴더나 scratchpad)에 스펙과 재료 파일을 같이 둡니다.

### 6. 만들기

```bash
cd <작업 폴더>
npm install pptxgenjs@3.12.0 sharp@0.33.5        # 처음 한 번 (node_modules가 없을 때)
node <이 스킬>/scripts/build_deck.js spec.json    # → output 경로의 .pptx + -대본.md
```
경고(넘침, 노트 없음)가 나오면 스펙을 고쳐 다시 만듭니다.

### 7. 검사 — 반드시 렌더해서 눈으로

```bash
python3 <이 스킬>/scripts/render_preview.py deck.pptx   # → deck-preview/slide-N.png, sheet-NN.png
```
- `sheet-*.png`(4장씩 묶음)를 Read로 **전부** 열어 봅니다. 글자 잘림 · 상자 밖으로 넘친 글자 · 겹침 · 빈 화면 · 한 슬라이드에 코랄이 두 군데 이상인지 봅니다.
- pptx 스킬이 있으면 `scripts/office/validate.py deck.pptx`로 파일 구조도 검사합니다.
- 고치고 다시 만들고 다시 렌더합니다. 문제가 없을 때까지.
- 렌더 결과 한글이 다른 글꼴로 보이면 그 PC에 글꼴이 없는 것입니다(아래 글꼴 참고). 배치 검사에는 큰 문제가 없지만, 가능하면 글꼴을 설치하고 봅니다.

### 7-1. 사용자 검토는 이미지로 먼저

사용자가 원하면 PPT 파일을 바로 넘기지 말고, 렌더한 슬라이드를 4~8장씩 묶은 이미지로 먼저 보여 주고 확인을 받는다. 확인이 끝나면 애니메이션까지 넣어 PPT로 만든다. 애니메이션은 이미지에 안 보이므로 어떤 슬라이드에서 무엇이 나타나는지 말로 함께 적는다.

### 8. 전달

`.pptx`와 대본 `.md`를 사용자에게 보내고(SendUserFile 등), 짧게 알립니다: 본 · 예비 장 수, 대본 기준 예상 시간, 차트 숫자의 출처(측정/사용자 데이터/예시), 사용자가 직접 확인할 것(글꼴 설치, 재구성 화면).

## 디자인 규칙 (엔진이 대부분 지키지만, 스펙을 쓸 때 알아야 할 것)

전체 규칙은 `references/design-system.md`에 있습니다(색 대비표, 글자 크기, 격자, 레이아웃). 스펙을 쓰다 색 · 크기를 직접 정해야 할 때 읽습니다.

- **코랄은 한 슬라이드에 한 곳.** 강조가 여러 개면 강조가 없는 것과 같습니다. 차트는 `highlight` 막대 하나, 글은 핵심 구절 하나.
- 장식 선 · 띠 · 그림자 · 그라데이션 · 아이콘은 넣지 않습니다. 여백과 카드 바탕색으로 나눕니다.
- 대비: 크림 위 코랄 글자는 24pt 이상 굵게만, 본문 크기 코랄 강조는 `coralText`. 크림 위 초록 · 틸 글자 금지(다크 코드 창 안에서만). 다크 위 에러색은 `errorOnDark`.
- 글자 크기: 본문 20pt, 표 16pt, 코드 13~15pt보다 작게 내리지 않습니다. 넘치면 글자를 줄이지 말고 내용을 덜어 내거나 슬라이드를 나눕니다.
- 순백(#FFFFFF) 바탕은 쓰지 않습니다(크림 #FAF9F5).

## 글꼴

기본: 제목 **Noto Serif KR**, 본문 **Pretendard**, 코드 **JetBrains Mono** (스펙 `fonts`로 바꿀 수 있음, 예: 제목 마루부리, 코드 D2Coding).
엔진은 테마의 라틴 · 동아시아(ea) · 한글(Hang) 글꼴 칸을 모두 채웁니다. pptxgenjs가 한글 칸을 비워 두면 한글만 맑은 고딕으로 나오기 때문입니다.

발표 PC에 글꼴이 없으면 다른 글꼴로 바뀝니다. 사용자에게 알릴 것:
- 설치는 **정적 OTF/TTF**(Pretendard는 `public/static` 폴더)로. Variable · woff 파일은 PowerPoint가 못 읽는 경우가 많습니다. 설치 후 PowerPoint를 완전히 껐다 켭니다.
- 다른 PC에서 발표하면 파일 › 옵션 › 저장 › "파일의 글꼴 포함"을 켜서 저장합니다.
- 테마 글꼴을 바꾸려면 디자인 › 변형 › 글꼴 › 글꼴 사용자 지정(한글 글꼴 칸까지).

## 파일

- `scripts/build_deck.js` — 엔진. 스펙 → .pptx + 대본
- `scripts/render_preview.py` — .pptx → PDF → 슬라이드 PNG + 4장 묶음
- `references/spec-format.md` — 스펙 형식 (슬라이드 · 블록 · 색 이름 · 높이 · 글꼴 굵기 · 애니메이션)
- `references/design-system.md` — 디자인 시스템 전체 (색 · 대비 · 글꼴 · 격자 · 구성 요소 · 레이아웃 · PowerPoint 설정)
- `assets/example-spec.json`, `assets/example/get-404.txt` — 예시 스펙과 그 스펙이 쓰는 실제 `curl -i` 응답

엔진에 없는 모양이 꼭 필요하면 `build_deck.js`의 `place()`에 블록 종류를 추가합니다. 이때도 위 디자인 규칙을 따르고, 추가한 블록을 `spec-format.md`에 적습니다.
