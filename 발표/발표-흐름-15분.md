## 2. API와 RESTful API (0:50)

**화면**

- [`그림/00-0-API와-RESTful-API.png`](그림/00-0-API와-RESTful-API.png): 위 → 왼쪽 → 가운데 → 오른쪽 순서로 짚는다

**대사**
> API는 프로그램끼리 요청과 응답을 주고받는 방법입니다. 우리가 만드는 API는 웹, 모바일 앱, 관리자 페이지, 다른 서비스가 모두 같이 씁니다. 그런데 API는 형식이 정해져 있지 않아서, 같은 "42번 글 삭제"도 만든 사람마다 왼쪽처럼 제각각일 수 있습니다. 그러면 쓰는 쪽은 API마다 문서를 찾거나 물어봐야 합니다. 그래서 REST라는 원칙으로 형식을 통일합니다. 자원은 URL로, 행동은 HTTP 메서드로, 결과는 상태 코드로 표현합니다. 이렇게 만든 API가 RESTful API입니다. `DELETE /api/v1/posts/42` 한 줄만 봐도 42번 글을 삭제한다는 걸 알 수 있습니다. 그럼 먼저, 이런 요청을 왜 보내는지부터 보겠습니다.

## 5. 자원 중심 URL (2:10)

**화면**

- [`그림/04-0-동사-URL의-문제.png`](그림/04-0-동사-URL의-문제.png): 왼쪽 패널 → 오른쪽 패널 순서로
- [`그림/04a-동사-URL과-자원-URL.png`](그림/04a-동사-URL과-자원-URL.png)
- [`그림/04b-자원-중심-URL.png`](그림/04b-자원-중심-URL.png)

**대사**
> **(04)** 먼저 URL입니다. URL에 동사를 넣으면 두 가지 문제가 생깁니다. 첫째, 같은 42번 글인데도 `getPost`, `updatePost`, `deletePost`처럼 기능마다 주소가 하나씩 늘어납니다. 그러면 쓰는 쪽은 찾아야 할 주소가 계속 늘고, 만드는 쪽은 같은 검증과 권한 확인을 주소마다 따로 걸어야 해서 하나만 빠뜨려도 버그나 보안 구멍이 됩니다. 둘째, 이름이 사람마다 다릅니다. 같은 조회를 누구는 `getPost`, 누구는 `fetchComment`, 누구는 `selectMember.do`라고 짓고, 파라미터 이름도 `id`, `no`, `mid`로 제각각입니다. 그래서 행동은 메서드에 맡기고 URL은 명사로 자원만 가리킵니다. 그러면 `/posts/42` 하나에 메서드만 바꿔 조회, 수정, 삭제를 하고, 댓글은 `/comments/7`, 회원은 `/members/3`처럼 누가 만들어도 같은 모양이 됩니다.
>
> **(04a)** 자주 쓰는 기능을 바꿔 보면 이렇습니다. 동사는 빠지고, 같은 주소에 메서드만 달라집니다. 특히 삭제를 GET으로 만들면 안 됩니다. GET은 데이터를 바꾸지 않는 요청으로 정의되어 있어서, 검색 엔진 크롤러나 메신저의 링크 미리보기는 사용자가 누르지 않아도 GET을 보냅니다. 삭제 URL을 메신저로 보내기만 해도 글이 지워질 수 있습니다.
>
> **(04b)** 명사 URL은 계층으로 짭니다. 글 목록은 `/posts`, 42번 글은 `/posts/42`, 그 글의 댓글은 `/posts/42/comments`, 그중 7번 댓글은 `/posts/42/comments/7`입니다. 중첩은 이렇게 글과 댓글, 자원 두 개까지를 기본으로 합니다. `/members/{memberId}/posts/{postId}/comments/{commentId}`처럼 더 이어지면 회원, 글, 댓글 id 세 개를 모두 알아야 해서 피합니다. 어떤 자원인지는 경로에, 정렬이나 개수처럼 보여 주는 방식은 물음표 뒤 쿼리에 둡니다. URL은 소문자와 하이픈으로 쓰고, 앞의 `/api/v1`은 버전입니다. 응답 구조를 크게 바꿔야 할 때 예전 앱이 깨지지 않도록 `/api/v2`를 따로 열기 위해 붙여 둡니다.

**화면**

- [`그림/05-메서드별-결과.png`](그림/05-메서드별-결과.png)

**대사**
> 다음은 메서드입니다. 같은 42번 글에 메서드만 바꿔 보내면 결과가 이렇게 달라집니다. GET은 조회, POST는 생성, DELETE는 삭제입니다. 헷갈리는 건 PUT과 PATCH입니다. 둘 다 제목만 보냈는데, PUT은 자원 전체를 교체해서 안 보낸 본문이 비워질 수 있고, PATCH는 보낸 필드만 바꿉니다. 그래서 일부 수정에는 PATCH를 씁니다. 하나 더, PUT과 DELETE는 여러 번 보내도 결과가 같지만, POST는 보낼 때마다 글이 하나씩 생깁니다. 그래서 글쓰기 버튼은 한 번 누르면 막아 두고, 결제처럼 중요한 POST는 중복 요청을 막는 처리를 합니다.

## 7. HTTP 상태 코드 (1:50)

**화면**

- [`그림/07-상태-코드-네-갈래.png`](그림/07-상태-코드-네-갈래.png)
- [`그림/07b-자주-만나는-에러-코드.png`](그림/07b-자주-만나는-에러-코드.png)

**대사**
> **(07)** 결과는 상태 코드로 알립니다. 첫 자리로 종류가 나뉩니다. 2xx는 성공, 3xx는 리다이렉트, 4xx는 요청한 쪽 문제, 5xx는 서버 문제입니다. API에서는 주로 2xx, 4xx, 5xx를 씁니다. 하지 말아야 할 게 하나 있습니다. 실패했는데 `200 OK`에 `success: false`를 담아 보내는 방식입니다. 모니터링, 프론트엔드의 에러 처리, 자동 재시도, 캐시는 바디를 읽지 않고 상태 코드만 봅니다. 그래서 실패를 200으로 주면 장애가 나도 알림이 오지 않고, 화면에는 저장 완료가 뜹니다. 세밀한 구분이 필요하면 상태 코드는 그대로 두고, 바디에 에러 코드를 따로 담습니다. 이건 바로 다음에 보겠습니다.
>
> **(07b)** 실무에서 에러가 나면 대부분 이 아홉 개 중 하나입니다. 가장 자주 보는 건 400, 401, 404, 500입니다. 400은 값이 빠졌거나 형식이 틀린 경우, 404는 자원이 없거나 URL이 틀린 경우, 500은 서버가 처리하지 못한 예외라 서버 로그를 봐야 합니다. 헷갈리는 401과 403은 실패한 단계가 다릅니다. 401은 JWT나 세션이 없거나 만료되어 누구인지 모르는 경우, 403은 누구인지는 알지만 권한이 없는 경우입니다. 502, 503, 504는 게이트웨이 뒤의 서버에 문제가 있을 때 나옵니다.

## 8. 공통 응답·에러 형식 (1:25)

**화면**

- [`그림/09-공통-에러-형식.png`](그림/09-공통-에러-형식.png): 왼쪽 통일 전 → 오른쪽 통일 후. 슬라이드 아래에 성공 응답 규칙 세 줄을 텍스트로 둔다: 단건은 자원 그대로 · 목록은 content + page · 필드는 camelCase, 날짜는 ISO-8601

**대사**
> 응답도 형식을 하나로 맞춥니다. 성공 응답은 단건이면 자원을 그대로, 목록이면 `content`와 `page`로 감싸서 주고, 필드 이름은 camelCase, 날짜는 ISO-8601로 통일합니다. 그럼 에러는 어떻게 보낼까요. 왼쪽처럼 API마다 에러 모양이 다르면, 프론트엔드는 API마다 에러를 꺼내는 코드를 따로 짜야 하고, 문장으로 분기했다가 백엔드가 문구를 고치면 깨집니다. 회원 API는 앞에서 말한 200 문제까지 있습니다. 그래서 오른쪽처럼 모든 API가 같은 형식으로 보냅니다. RFC 9457 표준의 type, title, status, detail에 우리 팀 에러 코드 `code`를 붙입니다. 프론트엔드는 에러 처리를 한 곳에만 쓰고, `code`로 분기하고, `detail` 문장은 화면에 보여 주기만 합니다. 스택 트레이스나 SQL 같은 내부 정보는 응답에 넣지 않고 서버 로그에만 남깁니다.

## 9. 전역 예외 처리와 입력 검증 (1:50)

**화면**

- [`그림/10-전역-예외-처리와-입력-검증.png`](그림/10-전역-예외-처리와-입력-검증.png)
- 코드 두 장면 (글자 크게)

```java
// 형식 검증: DTO에 규칙을 적어 두면 컨트롤러에 들어오기 전에 검사 (실패하면 400)
public record CreatePostRequest(
    @NotBlank @Size(max = 100) String title,
    @NotBlank String content) {}
```

```java
// 전역 예외 처리: 모든 예외를 한 곳에서 상태 코드 + 공통 에러 형식으로
@RestControllerAdvice
class GlobalExceptionHandler {
    @ExceptionHandler(ApiException.class)                    // 서비스가 던진 업무 예외 → 404, 409, 403
    ProblemDetail handle(ApiException e) { ... }
    @ExceptionHandler(MethodArgumentNotValidException.class) // @Valid 실패 → 400 + 틀린 필드
    ProblemDetail handleInvalid(...) { ... }
    @ExceptionHandler(Exception.class)                       // 예상 못 한 예외 → 로그 + 500
    ProblemDetail handleUnknown(Exception e) { ... }
}
```

**대사**
> **(10)** 이 형식을 모든 API가 지키게 하는 방법이 전역 예외 처리입니다. 요청은 입력 검증, 컨트롤러, 서비스, DB 순서로 처리되고, 성공하면 초록 화살표처럼 응답이 나갑니다. 실패는 두 종류입니다. 제목이 비었다처럼 값만 보면 아는 건 맨 앞의 입력 검증에서 400으로 돌려보냅니다. 글이 없다, 제목이 중복이다처럼 DB를 봐야 아는 건 서비스에서 예외를 던집니다. 던진 예외는 호출한 쪽으로 거꾸로 올라가서, 결국 아래의 전역 예외 처리기 한 곳에 모입니다. 여기서 상태 코드와 앞에서 본 공통 에러 형식으로 바꿔 응답합니다. 예상 못 한 예외는 로그를 남기고 500으로 답합니다.
>
> **(코드)** 코드로 보면 두 장면입니다. 위는 요청 DTO에 검증 규칙을 적은 것이고, 아래가 전역 예외 처리기입니다. 예외 종류마다 어떤 응답을 줄지 한 곳에 적어 두니, 컨트롤러마다 try-catch를 쓸 필요가 없고 에러 형식도 항상 같습니다. 화면에서 이미 검사했더라도 서버 검증은 생략하지 않습니다. API는 curl이나 Postman으로 화면 없이도 호출할 수 있기 때문입니다.

- [`그림/실제-화면/restdocs-2-응답.png`](그림/실제-화면/restdocs-2-응답.png)
- [`그림/13b-문서-만드는-방법.png`](그림/13b-문서-만드는-방법.png)

**대사**
> **(13)** 마지막은 문서입니다. 문서를 따로 쓰면 코드만 바뀌고 문서는 그대로 남기 쉽습니다. 그래서 코드에서 자동으로 만듭니다. 개발자가 컨트롤러에 설명 한 줄을 달면, 서버가 실행될 때 springdoc이 OpenAPI라는 표준 형식의 명세를 만들고, Swagger UI가 그걸 화면으로 보여 줍니다. 같은 색 글자가 코드에서 그대로 넘어온 정보입니다.
>
> **(swagger)** 실제 화면입니다. id에 42를 넣고 Execute를 누르면 실제로 요청이 나가고 200과 글 내용이 옵니다. 프론트 개발자는 묻지 않고 여기서 바로 호출해 볼 수 있습니다.
>
> **(restdocs)** Spring REST Docs로 만든 문서도 있습니다. 테스트가 실제로 주고받은 요청과 응답으로 만들어져서, 코드와 문서가 어긋나면 테스트가 실패합니다.
>
> **(13b)** 만드는 방법은 간단합니다. Swagger는 의존성 한 줄을 추가하고 서버를 켜면 끝이고, REST Docs는 API마다 테스트를 쓰면 문서가 만들어집니다. 시작은 Swagger, 정확도가 중요하면 REST Docs를 씁니다.

- 자주 나올 질문: **PUT vs PATCH**, **401 vs 403**, **200에 success:false 주면 안 되나**, **모든 서비스가 REST를 쓰나**, **Swagger와 REST Docs 차이**

| 질문 | 짧은 답 |
|---|---|
| 모든 서비스가 REST를 쓰나요? | 가장 흔하지만 전부는 아님. GraphQL, 서버끼리는 gRPC, 실시간은 WebSocket도 함께 씀 |
| 조회인데 조건이 너무 많으면? | 예외적으로 `POST /posts/search` + 바디로 받기도 함 |
| page는 0부터? 1부터? | Spring 기본은 0, 팀에서 정해 문서에 적음 |
| 정렬 필드는 왜 제한하나요? | 인덱스 없는 컬럼 정렬은 DB를 느리게 하고, 노출하면 안 되는 필드로 정보를 추측할 수 있음 |
| `/comments/7`처럼 쓰는 곳도 있던데요? | 둘 다 씀. `/posts/42/comments/7`은 소속이 주소에 보이고, `/comments/7`은 댓글 id만으로 부를 수 있음. 팀이 하나로 정함 (Q17-1) |
| 2단계를 넘으면 안 되나요? | 기본값일 뿐. GitHub 이슈처럼 번호가 저장소마다 1부터 다시 매겨지면 `/repos/{저장소}/issues/12`처럼 위 id가 꼭 필요해서 깊어짐 (Q17-2) |
| v2를 만들면 v1은? | 한동안 같이 운영하다가 대부분 업데이트하면 v1을 종료함 |
| OpenAPI와 Swagger는 같은 건가요? | OpenAPI는 문서 형식, Swagger UI는 그 문서를 보여 주는 화면 |
| 운영 서버에서도 Swagger가 열리나요? | 보통 개발·테스트 서버에서만 열고 운영에서는 끄거나 로그인 뒤에 둠 |
