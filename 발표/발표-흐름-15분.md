## 4. URL에는 자원만 쓴다 (0:45)

> 왼쪽처럼 URL에 동사를 넣으면 기능마다 주소가 늘어납니다. 그러면 권한 검사도 주소마다 걸어야 하고, 하나만 빠져도 보안 구멍이 됩니다. 그래서 주소에는 명사만 쓰고, 할 일은 메서드로 정합니다. 특히 GET으로 삭제하면 안 됩니다. 메신저의 링크 미리보기 같은 기능이 GET을 알아서 보내서, 링크를 공유만 해도 글이 지워질 수 있습니다. 그리고 주소는 대소문자를 구분해서 한 글자만 틀려도 404가 나니, 전부 소문자로 씁니다.

## 8. 메서드는 안전성과 멱등성으로 고른다 (0:45)

> 메서드를 고를 때는 두 가지를 봅니다. 첫째는 안전입니다. 서버의 데이터를 바꾸지 않는다는 뜻이고, 그래서 GET은 캐시가 저장하거나 미리 불러와도 괜찮습니다. 둘째는 멱등입니다. 같은 요청을 여러 번 보내도 결과가 같다는 뜻이고, 그래서 응답이 안 오면 그냥 다시 보내도 됩니다. PATCH가 세모인 이유는, 제목을 바꾸는 요청은 몇 번 보내도 같지만 조회수를 1 올리는 요청은 보낼 때마다 결과가 달라지기 때문입니다.

---

## 9. POST가 두 번 가면 두 번 만들어진다 (0:40)

> POST는 멱등이 아닙니다. 그래서 버튼을 두 번 누르거나 네트워크가 다시 보내면 결제가 두 번 될 수 있습니다. 버튼 비활성화로는 새로고침이나 다른 탭까지 막지 못해서, 중요한 요청은 서버에서 막습니다. 클라이언트가 요청마다 고유한 키를 보내고, 서버는 같은 키가 또 오면 다시 처리하지 않고 저장해 둔 결과를 돌려줍니다. 제 프로젝트에서도 이 방법으로 같은 글이 두 번 올라가지 않게 했습니다.

## 10. 자주 쓰는 상태 코드 (0:45)

> 자주 쓰는 상태 코드는 이 정도입니다. 몇 개만 짚겠습니다. 만들었으면 201과 함께 새 글의 주소를 주고, 지웠으면 바디 없이 204입니다. 가장 헷갈리는 건 401과 403입니다. 401은 누구인지 모를 때, 그러니까 로그인을 안 했거나 만료됐을 때입니다. 403은 누구인지는 알지만 권한이 없을 때입니다. 그리고 남의 비공개 글은 일부러 404를 주기도 합니다. 403을 주면 그 글이 있다는 게 드러나기 때문입니다.

*화면: 왼쪽은 안티패턴 예시, 오른쪽은 예제 서버의 실제 응답*

> 자주 보는 실수가 있습니다. 실패했는데 200을 주고, 바디에 success false를 담는 방식입니다. 문제는 모니터링, 캐시, 자동 재시도 같은 도구들이 바디는 안 보고 상태 코드만 본다는 겁니다. 그래서 장애가 나도 모니터링에는 전부 성공으로 찍힙니다. 실패는 4xx, 5xx로 보내고, 자세한 이유는 바디에 담습니다. 오른쪽은 예제 서버에 없는 글을 요청한 실제 응답입니다.

## 예비 슬라이드 (PPT 맨 뒤, 질문이 나오면)

### 30. 성공 응답은 감쌀까?

*질문이 나오면: 응답을 success/data로 감싸야 하나요?*

> 성공 응답을 success와 data로 감쌀지는 팀마다 다릅니다. 감싸면 프론트엔드에서 응답을 꺼내는 코드를 하나로 맞출 수 있고, 부가 정보를 넣기도 쉽습니다. 대신 success 필드는 상태 코드와 같은 정보를 한 번 더 보내는 셈입니다. 이걸로 분기하기 시작하면 앞에서 본 실패도 200으로 보내는 실수로 가기 쉽습니다. 어느 쪽이든 목록은 페이지 정보와 함께 감싸고, 필드 이름은 camelCase, 시각은 ISO 8601 형식으로 맞춥니다.

### 31. 버전: /api/v1

*질문이 나오면: 버전은 왜 붙이나요?*

> 버전은 응답 모양을 크게 바꿔야 할 때, 예전 클라이언트가 깨지지 않게 하려고 붙입니다. 칸을 새로 추가하는 건 괜찮습니다. 예전 클라이언트는 모르는 칸을 그냥 무시하니까요. 그래서 v1 그대로 둡니다. 칸을 빼거나 이름이나 타입을 바꿀 때만 v2를 만듭니다. 한동안 v1과 v2를 같이 운영하다가, v1 요청이 거의 없어지면 닫습니다. 웹만 있다면 서버와 화면을 같이 배포하면 되지만, 앱이나 외부 서비스가 쓰면 꼭 필요합니다.

### 32. 글결이 쓰는 상태 코드

*질문이 나오면: 실제 프로젝트에서는 어떤 코드를 썼나요?*

> 글결은 400, 401, 403, 404, 409, 429를 씁니다. 남의 비공개 글은 403이 아니라 404로 답합니다. 그래야 그 글이 있다는 사실조차 드러나지 않습니다.

### 33. REST Docs에 API 하나가 적힌 모양

*질문이 나오면: REST Docs는 어떻게 생겼나요?*

> 댓글 쓰기 API 하나가 적힌 모습입니다. 요청 헤더, 주소 안의 값, 요청 바디, 실제 요청, 실제 응답, 응답 칸 설명이 차례로 나옵니다. 모두 테스트가 실제로 주고받은 값입니다.

### 34. MSA에서 보는 502 · 503 · 504

*질문이 나오면: MSA에서는 에러가 어떻게 오나요?*

> MSA에서는 게이트웨이 뒤에 여러 서비스가 있습니다. 뒤쪽 서비스가 이상한 응답을 주면 502, 서비스가 과부하이거나 배포 중이면 503, 정해진 시간 안에 응답이 없으면 504입니다. 그리고 다른 서비스의 에러를 그대로 넘기지 않고, 우리 API의 에러 형식으로 바꿔서 돌려줍니다.

|---|---|
| REST를 꼭 지켜야 하나요? | 표준 규격이 아니라 설계 스타일. 안 지켜도 동작은 하지만, 팀 안에서 예측 가능하게 만드는 게 목적 |

| PATCH는 멱등인가요? | 값을 바꾸면 멱등, 조회수 +1처럼 연산을 보내면 멱등이 아님. 그래서 표에 세모 |

| 401과 403은? | 401 = 누구인지 모름 (로그인 안 함, 토큰·세션 만료). 403 = 누구인지 알지만 권한 없음 |
| 왜 403 대신 404를 주기도 해요? | 403을 주면 그 자원이 있다는 사실이 드러남. 비공개 글처럼 존재를 숨길 때 404 |
| RFC 7807과 9457은? | 9457이 2023년에 7807을 대체한 최신판. 필드는 type, title, status, detail, instance로 같음 |
| 성공 응답을 success/data로 감싸야 하나요? | 팀 선택. 감싸면 꺼내는 코드가 하나, 대신 success가 상태 코드와 중복. 목록은 어느 쪽이든 감쌈 |
| @RestControllerAdvice가 못 잡는 예외는? | 컨트롤러 밖에서 난 것. Security 필터, @Async, @Scheduled. 필터는 AuthenticationEntryPoint 등으로 따로 처리 |
| 화면에서 검사하는데 서버에서 또 해요? | API는 curl이나 Postman으로 화면 없이도 호출되니 서버 검증은 필수 |
| page는 0부터? 1부터? | Spring 기본은 0. 팀이 정해 문서에 적음 (글결은 1부터) |
| 정렬 필드는 왜 제한해요? | 인덱스 없는 컬럼 정렬은 DB를 느리게 하고, 노출하면 안 되는 필드로 정보를 추측할 수 있음 |
| 정렬을 여러 개 받는 이유는? | createdAt이 같은 글이 있으면 페이지마다 순서가 바뀜. 마지막에 id를 붙여 순서를 고정 |
| 오프셋은 글이 중복되거나 빠진다던데? | 보는 도중 새 글이 앞에 생기면 한 칸씩 밀려서 다음 쪽에 같은 글이 또 나옴. 글이 지워지면 하나를 건너뜀. 커서는 마지막으로 본 id 기준이라 이 문제가 없음 |
| 조회 조건이 너무 많으면? | 예외적으로 POST /posts/search + 바디로 받기도 함 |
| Swagger와 OpenAPI는 같은 건가요? | OpenAPI는 명세 형식, Swagger UI는 그 명세를 보여 주는 화면 |
| Swagger와 REST Docs를 같이 쓸 수 있나요? | restdocs-api-spec으로 REST Docs 테스트에서 OpenAPI 명세를 만들고 Swagger UI로 보여 줌 |
| 운영 서버에서도 Swagger가 열리나요? | 보통 개발 서버에서만 열고, 운영에서는 끄거나 로그인 뒤에 둠 |
| 모든 서비스가 REST를 쓰나요? | 가장 흔하지만 전부는 아님. GraphQL, 서버끼리는 gRPC, 실시간은 WebSocket도 씀 |
| (글결) 세션과 JWT는? | 세션은 서버가 상태를 들고 있어 로그아웃·만료를 바로 끊을 수 있음. JWT는 서버를 늘리기 쉽지만 발급한 토큰을 중간에 끊기 어려움. 글결을 세션으로 정한 이유는 직접 답함 |
| (글결) CSRF 토큰은 왜 보내요? | 세션 쿠키는 브라우저가 자동으로 붙여서 다른 사이트가 몰래 요청을 보낼 수 있음. GET이 아닌 요청은 쿠키와 머리글의 토큰이 같아야 처리 |
