## 4. URL에는 자원만 쓴다 (0:45)

> URL에 동사를 넣으면 기능마다 주소가 늘고, 같은 권한 검사를 주소마다 걸어야 해서 하나만 빠져도 구멍이 됩니다. 그래서 주소는 자원만 가리키고 행동은 메서드에 맡깁니다. 특히 GET으로 삭제하면 안 됩니다. 크롤러나 메신저의 링크 미리보기는 GET을 마음대로 보내서, 링크를 공유만 해도 글이 지워질 수 있습니다. 컬렉션은 복수형으로 통일하고, URL 경로는 대소문자를 구분해서 한 글자만 틀려도 404가 나니 전부 소문자로 쓰고 단어는 하이픈으로 나눕니다.

## 8. 메서드는 안전성과 멱등성으로 고른다 (0:45)

> 메서드를 고르는 기준은 두 가지입니다. 안전은 서버 상태를 바꾸지 않는다는 뜻이라, GET은 캐시나 프리페치가 마음대로 불러도 됩니다. 멱등은 여러 번 보내도 결과가 같다는 뜻이라, 타임아웃이 났을 때 그냥 다시 보내도 되는지 판단하는 기준이 됩니다. PUT은 자원 전체를 교체해서 안 보낸 칸이 비워질 수 있으니 일부 수정에는 PATCH를 씁니다. PATCH는 값을 바꾸면 멱등이지만, 조회수 1 증가처럼 연산을 보내면 멱등이 아니라서 세모입니다.

---

## 9. POST가 두 번 가면 두 번 만들어진다 (0:40)

> POST는 멱등이 아니라서 버튼을 두 번 누르거나 네트워크가 다시 보내면 두 번 처리됩니다. 버튼 비활성화는 화면 하나만 막을 뿐이라, 결제처럼 중요한 요청은 서버에서 막습니다. 클라이언트가 요청마다 고유한 키를 만들어 보내고, 서버는 같은 키가 다시 오면 처리하지 않고 저장해 둔 결과를 돌려줍니다. 제 프로젝트에서도 글쓰기 화면을 열 때 키를 만들어서 같은 글이 두 번 생기지 않게 했습니다.

## 10. 자주 쓰는 상태 코드 (0:40)

> 자주 쓰는 건 이 정도입니다. 생성은 201과 함께 Location 헤더에 새 자원의 주소를, 삭제는 바디 없이 204를 줍니다. 헷갈리는 건 401과 403입니다. 401은 누구인지 모르는 것, 403은 누구인지는 알지만 권한이 없는 것입니다. 409는 중복 가입이나 동시 수정처럼 현재 상태와 충돌할 때 씁니다. 그리고 남의 비공개 글처럼 존재 자체를 숨겨야 할 때는 일부러 403 대신 404를 주기도 합니다.

## 11. 실패를 200으로 보내면 (0:45)

*화면: 왼쪽은 안티패턴 예시, 오른쪽은 예제 서버의 실제 응답*

## 24. API 문서: Swagger와 REST Docs (0:50)

> 문서는 손으로 쓰면 코드와 금방 어긋나서 코드에서 만듭니다. Swagger는 springdoc 의존성만 넣으면 컨트롤러를 읽어 자동으로 만들고 화면에서 바로 호출해 볼 수 있지만, 설명을 붙이려면 운영 코드에 어노테이션이 늘어납니다. REST Docs는 테스트가 통과해야 문서가 생겨서 실제 동작과 어긋나지 않지만, API마다 테스트를 써야 합니다. 그래서 REST Docs 테스트로 OpenAPI 명세를 만들고 Swagger UI로 보여 주는 혼합 방식도 많이 씁니다.

## 29. 정리 (0:35)

> 정리하겠습니다. URL은 자원만, 행동은 메서드로 표현하고, 메서드는 안전성과 멱등성으로 고릅니다. 실패는 상태 코드로 알리고, 에러는 한 모양으로 보내되 내부 정보는 로그에만 남깁니다. 검증과 예외 처리는 한 곳에 모으고, 목록은 쿼리로 받되 서버가 한도를 정합니다. 그리고 이 규칙들은 코드에서 만든 문서로 공개합니다. 감사합니다.

## 예비 슬라이드 (PPT 맨 뒤, 질문이 나오면)

### 30. 성공 응답은 감쌀까?

*질문이 나오면: 응답을 success/data로 감싸야 하나요?*

> 성공 응답을 감쌀지는 팀마다 갈립니다. 감싸면 프론트엔드가 응답을 꺼내는 코드가 하나로 통일되고 메타 정보를 넣기 쉽습니다. 대신 success 필드는 상태 코드와 같은 정보를 두 번 보내는 셈이라, 이걸로 분기하다 보면 앞의 200 안티패턴으로 가기 쉽습니다. 어느 쪽이든 목록은 페이지 정보와 함께 감싸고, 필드는 camelCase, 시각은 ISO 8601로 맞춥니다.

### 31. 버전: /api/v1

*질문이 나오면: 버전은 왜 붙이나요?*

> 버전은 응답 구조를 깨는 변경이 필요할 때 예전 클라이언트를 지키려고 붙입니다. 칸을 더하는 건 예전 클라이언트가 모르는 칸을 무시하니 v1 그대로 두고, 칸을 빼거나 이름이나 타입을 바꿀 때만 v2를 엽니다. v1과 v2를 한동안 같이 운영하다가, v1 요청이 거의 없어지면 닫습니다. 웹만 쓰면 서버와 화면을 같이 배포하면 되지만, 앱이나 외부 서비스가 쓰면 꼭 필요합니다.

### 32. 글결이 쓰는 상태 코드

*질문이 나오면: 실제 프로젝트에서는 어떤 코드를 썼나요?*

> 글결은 400, 401, 403, 404, 409, 429를 씁니다. 남의 비공개 글은 403이 아니라 404로 답해서, 그 글이 있다는 사실도 드러나지 않게 했습니다.

### 33. REST Docs에 API 하나가 적힌 모양

*질문이 나오면: REST Docs는 어떻게 생겼나요?*

> 댓글 쓰기 하나에 요청 머리글, 주소 안의 값, 요청 본문 칸, 실제 요청, 실제 응답, 응답 칸이 차례로 적혀 있습니다. 모두 테스트가 실제로 주고받은 값입니다.

### 34. MSA에서 보는 502 · 503 · 504

*질문이 나오면: MSA에서는 에러가 어떻게 오나요?*

> MSA에서는 게이트웨이 뒤에 서비스가 여러 개 있습니다. 뒤쪽 서비스가 잘못된 응답을 주면 502, 과부하나 배포 중이면 503, 제한 시간 안에 응답이 없으면 504입니다. 그리고 다른 서비스의 에러를 그대로 넘기지 않고, 내 API의 에러 형식으로 바꿔서 돌려줍니다.

| REST를 꼭 지켜야 하나요? | 표준 규격이 아니라 설계 스타일. 안 지켜도 동작은 하지만, 팀 안에서 예측 가능하게 만드는 게 목적 |

| PATCH는 멱등인가요? | 값을 바꾸면 멱등, 조회수 +1처럼 연산을 보내면 멱등이 아님. 그래서 표에 세모 |

| 401과 403은? | 401 = 누구인지 모름 (로그인 안 함, 토큰·세션 만료). 403 = 누구인지 알지만 권한 없음 |
| 왜 403 대신 404를 주기도 해요? | 403을 주면 그 자원이 있다는 사실이 드러남. 비공개 글처럼 존재를 숨길 때 404 |
| RFC 7807과 9457은? | 9457이 2023년에 7807을 대체한 최신판. 필드는 type, title, status, detail, instance로 같음 |
| 성공 응답을 success/data로 감싸야 하나요? | 팀 선택. 감싸면 꺼내는 코드가 하나, 대신 success가 상태 코드와 중복. 목록은 어느 쪽이든 감쌈 |
| @RestControllerAdvice가 못 잡는 예외는? | 컨트롤러 밖에서 난 것. Security 필터, @Async, @Scheduled. 필터는 AuthenticationEntryPoint 등으로 따로 처리 |
| 화면에서 검사하는데 서버에서 또 해요? | API는 curl이나 Postman으로 화면 없이도 호출되니 서버 검증은 필수 |
| page는 0부터? 1부터? | Spring 기본은 0. 팀이 정해 문서에 적음 (글결은 1부터) |
| 정렬 필드는 왜 제한해요? | 인덱스 없는 컬럼 정렬은 DB를 느리게 하고, 노출하면 안 되는 필드로 정보를 추측할 수 있음 |
| 정렬을 여러 개 받는 이유는? | createdAt이 같은 글이 있으면 페이지마다 순서가 바뀜. 마지막에 id를 붙여 순서를 고정 |
| 조회 조건이 너무 많으면? | 예외적으로 POST /posts/search + 바디로 받기도 함 |
| Swagger와 OpenAPI는 같은 건가요? | OpenAPI는 명세 형식, Swagger UI는 그 명세를 보여 주는 화면 |
| Swagger와 REST Docs를 같이 쓸 수 있나요? | restdocs-api-spec으로 REST Docs 테스트에서 OpenAPI 명세를 만들고 Swagger UI로 보여 줌 |
| 운영 서버에서도 Swagger가 열리나요? | 보통 개발 서버에서만 열고, 운영에서는 끄거나 로그인 뒤에 둠 |
| 모든 서비스가 REST를 쓰나요? | 가장 흔하지만 전부는 아님. GraphQL, 서버끼리는 gRPC, 실시간은 WebSocket도 씀 |
| (글결) 세션과 JWT는? | 세션은 서버가 상태를 들고 있어 로그아웃·만료를 바로 끊을 수 있음. JWT는 서버를 늘리기 쉽지만 발급한 토큰을 중간에 끊기 어려움. 글결을 세션으로 정한 이유는 직접 답함 |
| (글결) CSRF 토큰은 왜 보내요? | 세션 쿠키는 브라우저가 자동으로 붙여서 다른 사이트가 몰래 요청을 보낼 수 있음. GET이 아닌 요청은 쿠키와 머리글의 토큰이 같아야 처리 |
