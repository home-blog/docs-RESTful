## 3. API = 식당 메뉴판 (1:15)

**화면**
- 그림: 손님(클라이언트) → 주문서(요청) → 주방(서버) → 음식(응답)
- 요청 한 장 예시 (색으로 네 부분 구분)

```http
POST /api/v1/posts                ← 메서드 + 주소
Content-Type: application/json    ← 헤더
{ "title": "제주도 3박 4일" }      ← 바디
```

- 응답 예시: `201 Created` + JSON

**대사**
> API는 프로그램끼리 대화하는 창구예요. 식당으로 치면 메뉴판과 주문 시스템입니다. 손님은 주방에 들어가지 않고 주문서만 내죠.
> 앱도 서버의 데이터베이스를 직접 열지 않고, 요청을 보내서 결과를 받아요.
> 요청은 네 부분이에요. **무엇을 할지(메서드), 어디에(주소), 부가 정보(헤더), 내용물(바디).** 응답은 결과 번호(상태 코드)와 내용물이 와요.

## 5. 자원 중심 URL (1:45)

**화면** (두 장)

1. [`그림/04a-동사-URL과-자원-URL.png`](그림/04a-동사-URL과-자원-URL.png): 동사가 들어간 URL ✗ → 메서드 + 명사 URL ✓
2. [`그림/04b-자원-중심-URL.png`](그림/04b-자원-중심-URL.png): URL 계층, 경로와 쿼리, 소문자·하이픈, 버전

**대사** (04a)
> URL에 get, create, update, delete 같은 동사를 넣으면, 같은 글 하나를 다루는데도 기능마다 URL이 늘어나고 이름 짓는 방식도 사람마다 달라집니다.
> REST에서는 행동은 HTTP 메서드로 표현하고, URL은 명사로 자원만 가리킵니다. 그래서 `/posts/42` 하나에 GET, PATCH, DELETE만 바꿔 보내 조회, 수정, 삭제를 합니다.
> 특히 삭제를 GET으로 만들면 안 됩니다. GET은 표준에서 데이터를 바꾸지 않는 요청으로 정의되어 있어서, 검색 엔진 크롤러나 메신저의 링크 미리보기는 사용자가 누르지 않아도 URL에 GET을 보냅니다. 삭제 URL을 메신저로 보내기만 해도 글이 지워질 수 있습니다.

**대사** (04b)
> 명사 URL은 계층으로 짭니다. 컬렉션은 복수형 `/posts`, 그중 하나는 `/posts/42`, 하위 자원은 `/posts/42/comments`입니다.
> 중첩은 2단계까지만 둡니다. `/members/3/posts/42/comments/7`처럼 깊어지면 댓글 하나를 보려고 회원 id와 글 id를 모두 알아야 하고, 서버는 단계마다 관계가 맞는지 확인해야 합니다. 댓글 7번은 id만으로 이미 하나로 정해지므로, 깊어지면 `/comments/7`처럼 끊습니다.
> 특정 자원을 가리키는 값은 경로에, 정렬이나 개수처럼 보여 주는 방식을 바꾸는 값은 물음표 뒤 쿼리에 둡니다.
> URL은 소문자로 쓰고 단어 사이는 하이픈으로 잇습니다.
> 앞에 붙은 `/api/v1`은 버전입니다. 예를 들어 작성자 `author`를 문자열 `"kim"`에서 객체 `{ id, nickname, profileImage }`로 바꾸면, 이미 사용자 폰에 설치된 예전 앱은 바뀐 응답을 읽지 못해 오류가 납니다. 앱은 사용자가 업데이트하기 전까지 예전 버전으로 남아 있기 때문입니다. 그래서 구조를 크게 바꿀 때는 `/api/v2`를 새로 열고 v1은 그대로 둡니다. 예전 앱은 v1을, 새 앱은 v2를 쓰다가, 대부분 업데이트하면 v1을 종료합니다. 필드를 추가하는 정도는 예전 앱이 무시하면 되므로 버전을 올리지 않습니다.

## 6. HTTP 메서드 + 멱등 (1:45)

**화면**

| 메서드 | 뜻 | 예 |
|---|---|---|
| GET | 조회 | `GET /posts/42` |
| POST | 생성 | `POST /posts` |
| PUT | 통째로 교체 | `PUT /posts/42` |
| PATCH | 일부 수정 | `PATCH /posts/42` |
| DELETE | 삭제 | `DELETE /posts/42` |

그림 두 개: 🛗 엘리베이터 버튼(멱등: PUT, DELETE) vs 🥤 자판기 버튼(멱등 아님: POST)

**대사**
> 메서드는 다섯 개만 기억하세요. 조회, 생성, 교체, 수정, 삭제.
> 헷갈리는 게 PUT과 PATCH인데요, **PUT은 서류를 통째로 갈아 끼우는 것**, **PATCH는 수정 테이프로 일부만 고치는 것**이에요. 제목만 고치려고 PUT을 쓰면 본문이 날아갈 수 있어서, 수정 기능은 보통 PATCH를 씁니다.
> 하나 더. **엘리베이터 버튼은 열 번 눌러도 한 번 와요.** 이걸 멱등이라고 하는데, PUT과 DELETE가 그래요. 반면 **POST는 자판기 버튼**이라 열 번 누르면 글이 열 개 생겨요. 그래서 "글 쓰기" 버튼은 한 번 누르면 막아 두는 거예요.

## 7. HTTP 상태 코드 (2:30)

**화면** (세 장)

1. [`그림/07-상태-코드-네-갈래.png`](그림/07-상태-코드-네-갈래.png): 2xx · 3xx · 4xx · 5xx, 실패를 200으로 주지 않기
2. [`그림/07b-자주-만나는-에러-코드.png`](그림/07b-자주-만나는-에러-코드.png): 자주 만나는 에러 코드 9개와 먼저 확인할 것
3. [`그림/08-401과-403.png`](그림/08-401과-403.png): 인증 실패(401)와 인가 실패(403)

**대사** (07)
> 상태 코드는 첫 자리로 결과의 종류를 나눕니다. 2xx는 성공, 3xx는 리다이렉트, 4xx는 클라이언트 오류, 5xx는 서버 오류입니다. 3xx는 REST API에서는 드물게 쓰고, 주로 다루는 건 2xx, 4xx, 5xx입니다.
> 하지 말아야 할 것이 하나 있습니다. 실패했는데 `200 OK`에 `success: false`를 담아 보내는 방식입니다. 모니터링, 프론트엔드의 에러 처리, 자동 재시도, 캐시는 응답 바디를 읽지 않고 상태 코드만 봅니다. 그래서 실패를 200으로 주면 장애가 나도 알림이 오지 않고, 화면에는 저장 완료가 뜨고, 실패 응답이 캐시될 수 있습니다.
> 이렇게 하는 곳이 있는 이유는, 통신 자체는 성공했으니 200이라고 보거나, 상태 코드보다 세밀한 에러 구분이 필요해서입니다. 세밀한 구분은 상태 코드를 버리지 않고 바디의 에러 코드로 하면 됩니다. 상태 코드로 큰 분류를, 바디의 code로 세부 원인을 줍니다.

**대사** (07b)
> 실무에서 에러가 나면 대부분 이 아홉 가지 중 하나입니다. 가장 자주 보는 건 400, 401, 404, 500입니다. 400은 필수 값이 빠졌거나 형식이 틀린 경우, 401은 JWT나 세션 같은 인증 정보가 없거나 만료된 경우, 404는 자원이 없거나 URL이 틀린 경우, 500은 서버에서 처리하지 못한 예외라 서버 로그를 봐야 합니다. 502, 503, 504는 게이트웨이 뒤의 서버에 문제가 있을 때 나옵니다.

**대사** (08)
> 401과 403은 실패한 단계가 다릅니다. 401은 인증 실패로, JWT나 세션 같은 인증 정보가 없거나 만료되어 누구인지 확인하지 못한 경우입니다. 403은 인가 실패로, 누구인지는 확인했지만 이 작업을 할 권한이 없는 경우입니다. 다른 사람의 글을 삭제하려 하면 403입니다.

## 8. 공통 응답·에러 형식 (2:00)

**화면**: [`그림/09-공통-에러-형식.png`](그림/09-공통-에러-형식.png) (왼쪽 통일 전, 오른쪽 통일 후)

| | 통일 전 | 통일 후 |
|---|---|---|
| 에러 꺼내는 코드 | API마다 다름 | 한 곳 |
| 새 API가 생기면 | 에러 모양을 물어봐야 함 | 그대로 처리됨 |
| 원인 구분 | 문장을 읽어야 함 | `code`로 구분 |
| 문구를 바꾸면 | 분기가 깨짐 | 영향 없음 |
| 내부 정보 | 새기 쉬움 | 형식에 없는 건 안 나감 |

**대사** (왼쪽, 통일 전)
> 왼쪽은 API마다 에러를 다르게 보내는 경우입니다. 글 API는 `error` 필드에, 댓글 API는 `msg` 필드에 담고, 회원 API는 실패인데 200과 문자열 `"FAIL"`을 보냅니다.
> 그러면 프론트엔드는 API마다 에러를 꺼내는 코드를 따로 짜야 합니다. 새 API가 생길 때마다 에러를 어떻게 주는지 물어봐야 하고, 토큰 만료 같은 공통 처리도 한 곳에 모을 수 없습니다.
> 원인도 구분하기 어렵습니다. `"not found"`만으로는 무엇이 없는지 알 수 없습니다. 그래서 `msg === "글이 없습니다"`처럼 문장으로 분기하게 되는데, 백엔드가 문구를 고치는 순간 그 분기는 동작하지 않습니다.

**대사** (오른쪽, 통일 후)
> 그래서 모든 API가 같은 모양으로 에러를 보내게 맞춥니다. 형식은 RFC 9457이라는 표준을 씁니다. `type`은 에러 종류, `title`은 짧은 제목, `status`는 상태 코드, `detail`은 이번 요청에서 무엇이 잘못됐는지에 대한 설명입니다. 여기에 우리 팀이 정한 에러 코드 `code`를 하나 추가합니다. Spring Boot도 이 형식을 기본으로 지원합니다.
> 이제 프론트엔드는 에러 처리를 한 곳에만 쓰면 됩니다. 프로그램은 `code`로 분기하고, `detail` 문장은 화면에 보여 주기만 합니다. 그래서 문구를 바꾸거나 번역해도 분기가 깨지지 않습니다.
> 마지막으로 스택 트레이스나 SQL 같은 내부 정보는 응답에 넣지 않습니다. 서버 내부 구조가 드러나 공격의 힌트가 되기 때문입니다. 자세한 내용은 서버 로그에만 남깁니다.

```java
@RestControllerAdvice
class GlobalExceptionHandler {
    @ExceptionHandler(ApiException.class)                    // 서비스가 던진 업무 예외 → 404, 409, 403
    ProblemDetail handle(ApiException e) { ... }
    @ExceptionHandler(MethodArgumentNotValidException.class) // @Valid 실패 → 400 + 틀린 필드
    ProblemDetail handleInvalid(...) { ... }
    @ExceptionHandler(Exception.class)                       // 예상 못 한 예외 → 로그 + 500
    ProblemDetail handleUnknown(Exception e) { ... }
}
```

그림 읽는 법

| 표시 | 뜻 |
|---|---|
| 윗줄 가로 화살표 | 요청이 처리되는 순서: 입력 검증 → 컨트롤러 → 서비스 → DB |
| 초록 (위) | 성공 응답이 나가는 길 (200 · 201 · 204) |
| 주황 (아래로) | 예상한 실패: 요청이 잘못됐거나 업무 규칙 위반 (4xx) |
| 빨강 (아래로) | 예상 못 한 실패: 서버 쪽 문제 (5xx) |
| 아래 큰 상자 → 청록 | 모든 실패가 모여 같은 형식으로 응답되는 길 |

**대사** (그림: 처리 순서)
> 이 그림은 요청 하나가 서버 안에서 지나가는 길입니다. 글 쓰기 요청을 예로 들면, 위쪽 줄을 따라 입력 검증, 컨트롤러, 서비스, DB 순서로 처리됩니다.
> 입력 검증이 맨 앞에 있는 이유는, 제목이 비었다처럼 값만 보고 판단할 수 있는 문제는 DB까지 갈 필요 없이 가장 먼저 돌려보내는 게 가장 싸기 때문입니다. 여기서 실패하면 400입니다.
> 컨트롤러는 요청을 서비스에 넘기고, 결과를 HTTP 응답으로 바꾸는 일만 합니다. 성공하면 초록 화살표처럼 컨트롤러가 200이나 201을 돌려줍니다.
> 서비스는 업무 규칙을 검사합니다. 글이 있는지, 제목이 중복인지, 작성자 본인인지는 DB를 조회해야 알 수 있어서 입력 검증에서 미리 할 수 없습니다. 그래서 검증을 값만 보면 아는 것과 DB를 봐야 아는 것, 두 종류로 나눕니다. 서비스에서 실패하면 404, 409, 403이 됩니다.

**대사** (그림: 실패가 모이는 곳)
> 서비스는 실패를 반환값이 아니라 예외로 알립니다. 예외를 던지면 그 자리에서 처리가 멈추고, `@Transactional`이 그때까지의 DB 작업을 되돌려서 중간까지만 저장되는 일이 없습니다. 서비스는 "글이 없다"는 사실만 알리고, 그걸 404로 바꾸는 건 다음 단계가 맡습니다.
> 예외는 호출한 쪽으로 거꾸로 올라갑니다. 중간에 아무도 잡지 않으니, 어디서 실패하든 결국 아래의 전역 예외 처리기 한 곳에 도착합니다. 여기서 예외 종류를 보고 상태 코드와 슬라이드 8의 공통 에러 형식으로 바꿔 응답합니다. DB 연결 끊김처럼 예상 못 한 예외는 로그에 자세히 남기고, 응답은 500으로 간단히 줍니다.

**대사** (코드)
> 컨트롤러마다 try-catch를 쓰면 컨트롤러가 50개일 때 같은 코드가 50번 반복되고, 사람마다 에러 형식을 다르게 만들고, 누가 catch를 빠뜨리면 그 API만 다른 에러가 나갑니다. 슬라이드 8의 "통일 전" 문제가 바로 여기서 생깁니다.
> 처리를 한 곳에 모으면 에러 형식이 항상 같고, 컨트롤러와 서비스는 정상 흐름만 쓰면 되고, 예상 못 한 예외까지 빠짐없이 받습니다. 그래서 그림의 컨트롤러에는 try-catch가 없습니다.
> 마지막으로, 화면에서 이미 검사했더라도 서버 검증은 생략하지 않습니다. API는 curl이나 Postman으로 직접 호출할 수 있고, 개발자 도구에서 값을 고쳐 보낼 수도 있습니다. 화면 검증은 사용자 편의를 위한 것이고, 서버 검증은 데이터를 지키는 마지막 방어선입니다.

## 10. 페이징·검색·정렬 (1:30)

**화면**

| 순서 | 화면 | 말할 것 | 시간 |
|---|---|---|---|
| ① 문제 | 주소 1단계 | 목록 API가 정해야 할 세 가지 | 10초 |
| ② 요청 | 주소 2~4단계 | 한 조각씩 붙이며 설명 + 왜 쿼리에 넣나 | 40초 |

| ⑤ 방식 | 11b 그대로 | 오프셋 vs 커서 한 문장 | 5초 |

**대사**
> **(① 1단계)** 글 목록 API를 만들 때는 세 가지를 정해야 합니다. 어떤 글을 보여 줄지, 어떤 순서로 보여 줄지, 한 번에 몇 개씩 보여 줄지입니다. 글이 100만 개면 한 번에 줄 수 없으니까요.
>
> **(② 2단계)** 이 세 가지는 모두 물음표 뒤 쿼리 스트링으로 받습니다. `topic`과 `keyword`는 검색입니다. 여행 주제이면서 제주가 들어간 글만 달라는 뜻입니다.
> **(3단계)** `sort=createdAt,desc`는 정렬입니다. 작성 시각 기준 내림차순, 즉 최신순입니다.
> **(4단계)** `page`와 `size`는 페이징입니다. 0번째 묶음을 20개씩 달라는 뜻입니다.
> 경로가 아니라 쿼리에 넣는 이유는, 앞에서 말했듯 경로는 어떤 자원인지를 가리키기 때문입니다. 조건을 바꿔도 대상은 같은 글 목록이고, 보여 주는 방식만 달라집니다. 쿼리는 이름=값 형태라 각 값의 뜻이 보이고, 필요한 것만 넣으면 되고, 아무것도 안 보내면 최신순 20개가 기본으로 옵니다.
>
> **(③ 11b)** 응답에는 글 목록과 함께 페이지 정보를 줍니다. 전체 글 수와 전체 묶음 수를 알아야 화면에 페이지 번호나 다음 버튼을 그릴 수 있기 때문입니다. 결과가 없으면 404가 아니라 200과 빈 배열을 줍니다.
>
> **(④ 11b 아래 줄)** 대신 서버는 세 가지를 제한합니다. `size`는 최대 100까지, 정렬은 정해 둔 필드로만, 정렬 조건이 없으면 최신순으로 합니다. `size=1000000` 같은 요청 하나로 서버가 멈추면 안 되니까요.
>
> **(⑤)** 페이지 번호가 있는 게시판은 지금 본 `page` 방식을, 무한 스크롤은 마지막으로 본 글 다음부터 가져오는 커서 방식을 씁니다.

**말하지 않을 것**: `?`·`&`·`=` 기호 설명, 한글 인코딩, Spring Data 내부 형식, 오프셋과 커서의 자세한 차이 (질문이 나오면 답한다)

**질문이 나오면**

| 질문 | 답 |
|---|---|
| 조회인데 조건이 너무 많으면? | 예외적으로 `POST /posts/search` + 바디로 받기도 함 |
| page는 0부터? 1부터? | Spring 기본은 0, 팀에서 정해서 문서에 적음 (예상 질문 Q7) |
| 오프셋과 커서 차이는? | 예비 슬라이드(그림 12)를 보여 준다 |
| 검색 결과가 0개면? | 404가 아니라 200 + 빈 배열 |
| 정렬 필드는 왜 제한하나? | 인덱스 없는 컬럼으로 정렬하면 DB가 느려지고, 노출하면 안 되는 필드로 정렬해 정보를 추측할 수 있음 |

## 11. API 문서 작성 (2:00)

**화면**: [`그림/13-API-문서가-만들어지는-길.png`](그림/13-API-문서가-만들어지는-길.png) (왼쪽부터 1 → 2 → 3 순서로 손으로 짚으며)

그림 읽는 법
- 세 칸은 같은 API(`GET /api/v1/posts/{id}`)가 코드 → 명세 → 화면으로 바뀌는 과정이다.
- 같은 색은 같은 정보다. 파랑 `글 하나 조회`, 초록 `/api/v1/posts/{id}`, 주황 `id`가 세 칸에 모두 나온다.

**대사**
> **(문제)** API를 만들면 프론트 개발자는 어떤 주소에 어떤 값을 보내야 하는지, 무엇이 돌아오는지 알아야 합니다. 문서가 없으면 매번 메신저로 물어봐야 하고, 문서를 따로 써 두면 코드는 바뀌었는데 문서는 그대로인 일이 생깁니다.
>
> **(1번 칸)** 그래서 문서를 코드에서 자동으로 만듭니다. 개발자는 평소처럼 컨트롤러를 쓰고, `@Operation`으로 "글 하나 조회"라는 설명 한 줄만 덧붙입니다.
>
> **(2번 칸)** 서버를 실행하면 springdoc이라는 라이브러리가 이 코드를 읽어서, 가운데 같은 JSON을 자동으로 만듭니다. 주소, 설명, 파라미터 `id`, 응답 코드 200과 404가 들어 있습니다. 이 JSON의 형식이 OpenAPI라는 표준입니다. 개발자가 직접 쓰는 파일이 아닙니다.
>
> **(3번 칸)** 브라우저로 swagger-ui 주소를 열면, Swagger UI가 이 JSON을 오른쪽처럼 화면으로 보여 줍니다. 같은 색 글자가 1번 코드에서 그대로 넘어온 것입니다. 여기서 `id`에 42를 넣고 Execute를 누르면 실제로 API가 호출되고 응답이 보입니다.
>
> **(정리)** 정리하면 OpenAPI는 문서의 형식, springdoc은 그 문서를 코드에서 만들어 주는 도구, Swagger UI는 그 문서를 보여 주는 화면입니다. 코드를 고치면 문서도 같이 바뀌고, 프론트 개발자는 묻지 않고 이 화면에서 바로 호출해 볼 수 있습니다.
> 문서가 실제 동작과 절대 어긋나면 안 되는 경우에는, 테스트가 통과해야 문서가 만들어지는 Spring REST Docs를 쓰기도 합니다.

| springdoc과 REST Docs 중 뭘 써요? | 시작은 springdoc(설정만 하면 바로 생김), 정확도가 중요하면 REST Docs |
