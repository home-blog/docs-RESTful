## 2. API와 RESTful API (1:05 · 클릭 2번)

> API는 프로그램끼리 요청과 응답을 주고받는 방법입니다. 우리가 만드는 API는 웹, 모바일 앱, 관리자 페이지, 다른 서비스가 모두 같이 씁니다. **[▶ 클릭 1 · 왼쪽 코드]** 그런데 API는 형식이 정해져 있지 않아서, 같은 "42번 글 삭제"도 만든 사람마다 왼쪽처럼 제각각일 수 있습니다. 그러면 쓰는 쪽은 API마다 문서를 찾거나 물어봐야 합니다. **[▶ 클릭 2 · 오른쪽 코드]** 그래서 REST라는 원칙으로 형식을 통일합니다. 자원은 URL로, 행동은 HTTP 메서드로, 결과는 상태 코드로 표현합니다. 이렇게 만든 API가 RESTful API입니다. DELETE /api/v1/posts/42 한 줄만 봐도 42번 글을 삭제한다는 걸 알 수 있습니다. 그럼 먼저, 이런 요청을 왜 보내는지부터 보겠습니다.

## 3. 왜 요청을 보내나 (0:30)

> 웹이나 앱 화면에 보이는 글, 댓글, 회원 정보는 사용자 기기가 아니라 서버의 DB에 있습니다. 그래서 화면은 데이터가 필요할 때마다 서버에 요청을 보냅니다. 첫 화면을 열면 글 목록을 조회하는 GET이, 저장 버튼을 누르면 글을 만드는 POST가 나갑니다. 사용자의 동작 하나가 HTTP 요청 하나입니다.

## 13. 같은 42번 글에 메서드만 바꾸면 (0:55 · 클릭 1번)

> 같은 42번 글에 메서드만 바꿔 보내면 결과가 이렇게 달라집니다. GET은 조회, POST는 생성, DELETE는 삭제입니다. 헷갈리는 건 PUT과 PATCH입니다. 둘 다 제목만 보냈는데, PUT은 자원 전체를 교체해서 안 보낸 본문이 비워질 수 있고, PATCH는 보낸 필드만 바꿉니다. 그래서 일부 수정에는 PATCH를 씁니다. **[▶ 클릭 1 · 아래 멱등 줄]** 하나 더, PUT과 DELETE는 여러 번 보내도 결과가 같지만, POST는 보낼 때마다 글이 하나씩 생깁니다. 그래서 글쓰기 버튼은 한 번 누르면 막아 두고, 결제처럼 중요한 POST는 중복 요청을 막는 처리를 합니다.

## 14. 결과는 상태 코드로 (1:05 · 클릭 1번)

> 결과는 상태 코드로 알립니다. 첫 자리로 종류가 나뉩니다. 2xx는 성공, 3xx는 리다이렉트, 4xx는 요청한 쪽 문제, 5xx는 서버 문제입니다. API에서는 주로 2xx, 4xx, 5xx를 씁니다. **[▶ 클릭 1 · 아래 코드 창]** 하지 말아야 할 게 하나 있습니다. 실패했는데 200 OK에 success: false를 담아 보내는 방식입니다. 모니터링, 프론트엔드의 에러 처리, 자동 재시도, 캐시는 바디를 읽지 않고 상태 코드만 봅니다. 그래서 실패를 200으로 주면 장애가 나도 알림이 오지 않고, 화면에는 저장 완료가 뜹니다. 세밀한 구분이 필요하면 상태 코드는 그대로 두고, 바디에 에러 코드를 따로 담습니다. 이건 바로 다음에 보겠습니다.

## 15. 자주 만나는 에러 코드 (0:50)

> 실무에서 에러가 나면 대부분 이 아홉 개 중 하나입니다. 가장 자주 보는 건 400, 401, 404, 500입니다. 400은 값이 빠졌거나 형식이 틀린 경우, 404는 자원이 없거나 URL이 틀린 경우, 500은 서버가 처리하지 못한 예외라 서버 로그를 봐야 합니다. 헷갈리는 401과 403은 실패한 단계가 다릅니다. 401은 JWT나 세션이 없거나 만료되어 누구인지 모르는 경우, 403은 누구인지는 알지만 권한이 없는 경우입니다. 502, 503, 504는 게이트웨이 뒤의 서버에 문제가 있을 때 나옵니다.

## 예비 슬라이드 (맨 뒤, 질문이 나오면)

### 36. 위 id를 빼도 되는 경우

*질문이 나오면: /comments/7처럼 위 id를 빼도 되는 이유는?*

> 댓글은 번호가 전체에서 하나라서, 7번 댓글을 찾으면 그 줄에 글 번호 42도 들어 있습니다. 그래서 /comments/7만으로 충분합니다. GitHub 이슈는 번호가 저장소마다 1부터 다시 매겨져서, 12번 이슈가 여러 개입니다. 그래서 저장소를 주소에 꼭 넣어야 합니다.

### 37. 멱등성

*질문이 나오면: 멱등성이 뭔가요? 재시도는 왜 안전한가요?*

> 멱등은 여러 번 보내도 서버 상태가 한 번 보낸 것과 같다는 뜻입니다. DELETE는 두 번째부터 404가 오지만 42번 글이 없는 상태는 같아서 멱등입니다. POST는 보낼 때마다 글이 하나씩 생겨서 멱등이 아니고, 그래서 중복을 막아야 합니다.

### 38. 401과 403

*질문이 나오면: 401과 403은 뭐가 다른가요?*

> 401과 403은 실패한 단계가 다릅니다. 먼저 로그인했는지 확인하는 인증에서 실패하면 401, 로그인은 했지만 이 글을 지울 권한이 없으면 403입니다. 401은 누구인지 모르는 것, 403은 누구인지 알지만 권한이 없는 것입니다.

### 39. 오프셋과 커서

*질문이 나오면: 오프셋과 커서 페이징은 뭐가 다른가요?*

> 오프셋은 쪽 번호로 앞의 글을 세면서 건너뛰어서, 원하는 쪽으로 바로 갈 수 있지만 뒤로 갈수록 느려집니다. 커서는 마지막으로 본 글 번호 다음부터 가져와서 데이터가 많아도 빠르지만, 특정 쪽으로 바로 가기는 어렵습니다. 그래서 게시판은 오프셋, 무한 스크롤은 커서를 씁니다.

### 40. 글결이 쓰는 상태 코드

*질문이 나오면: 글결에서는 어떤 상태 코드를 쓰나요?*

> 글결은 400, 401, 403, 404, 409, 429를 씁니다. 남의 비공개 글은 403이 아니라 404로 답해서, 그 글이 있다는 사실도 드러나지 않게 했습니다.

### 41. REST Docs에 API 하나가 적힌 모양

*질문이 나오면: REST Docs에 API 하나가 어떻게 적혀 있나요?*

> 댓글 쓰기 하나에 요청 머리글, 주소 안의 값, 요청 본문 칸, 실제 요청, 실제 응답, 응답 칸이 차례로 적혀 있습니다. 모두 테스트가 실제로 주고받은 값입니다.

### 42. 단일 서버의 요청 흐름

*질문이 나오면: 실제 서버 안에서 요청이 어떻게 처리되나요?*

> Spring Boot 애플리케이션 하나에서는 인증 필터, URL 매핑, 컨트롤러, 서비스, DB 순서로 처리됩니다. 댓글 서비스가 글이 있는지 확인할 때도 같은 프로세스 안의 메서드 호출이라 빠릅니다. 대신 일부 기능만 따로 배포하거나 늘리기는 어렵습니다.

### 43. MSA의 요청 흐름

*질문이 나오면: MSA에서는 어떻게 되나요?*

> MSA에서는 API Gateway가 먼저 인증하고, 주소를 보고 맞는 서비스로 보냅니다. 댓글 서비스가 글이 있는지 확인할 때는 글 서비스에 HTTP로 물어봐야 합니다. 그래도 클라이언트가 보내는 요청은 단일 서버와 똑같습니다.

### 44. MSA에서 에러가 전달되는 흐름

*질문이 나오면: MSA에서 에러는 어떻게 전달되나요?*

> 에러 형식이 모든 서비스에서 같으면, 글 서비스의 404와 POST_NOT_FOUND가 그대로 클라이언트까지 전달됩니다. 글 서비스가 꺼져 있으면 503, 제한 시간 안에 답이 없으면 504처럼 원인에 맞는 코드로 답합니다.

| (글결) 세션과 JWT는 뭐가 다른가요? | 세션은 서버가 로그인 상태를 들고 있어 로그아웃·만료를 서버에서 바로 끊을 수 있음. JWT는 서버가 상태를 들지 않아 서버를 늘리기 쉽지만, 발급한 토큰을 중간에 끊기 어려움. 글결을 세션으로 정한 이유는 발표자가 직접 답함 |
| 정렬 필드는 왜 제한하나요? | 인덱스 없는 컬럼 정렬은 DB를 느리게 하고, 노출하면 안 되는 필드로 정보를 추측할 수 있음 |
| /comments/7처럼 쓰는 곳도 있던데요? | 둘 다 씀. /posts/42/comments/7은 소속이 주소에 보이고, /comments/7은 댓글 id만으로 부를 수 있음. 팀이 하나로 정함 |
| 2단계를 넘으면 안 되나요? | 기본값일 뿐. GitHub 이슈처럼 번호가 저장소마다 1부터 다시 매겨지면 /repos/{저장소}/issues/12처럼 위 id가 꼭 필요해서 깊어짐 |
| (글결) v1은 언제 v2로 바꾸나요? | 글결은 칸을 더하는 변경은 v1 그대로, 칸을 빼거나 뜻을 바꿀 때만 v2를 염. 웹만 쓰면 꼭 필요하진 않지만 앱이나 외부가 쓰게 되면 필요 |
| v2를 만들면 v1은? | 한동안 같이 운영하다가 대부분 옮겨 가면 v1을 종료함 |
| OpenAPI와 Swagger는 같은 건가요? | OpenAPI는 문서 형식, Swagger UI는 그 문서를 보여 주는 화면 |
| 운영 서버에서도 Swagger가 열리나요? | 보통 개발·테스트 서버에서만 열고 운영에서는 끄거나 로그인 뒤에 둠 |
| 왜 Entity를 그대로 안 받고 DTO를 쓰나요? | Entity를 그대로 받으면 role 같은 받으면 안 되는 칸까지 바뀔 수 있고, 그대로 응답하면 password 같은 내부 정보가 나감. DTO로 받을 칸 · 보여 줄 칸을 정하고, 검증 규칙도 DTO에 적음 |
| 컨트롤러에서는 예외를 안 잡나요? | 잡지 않고 통과시킴. 잡으면 API마다 에러 응답 코드를 반복하고 형식이 깨지기 쉬움. 실패해도 정상 응답을 내야 하는 경우(기본값으로 대신하기)만 따로 처리 |
| 응답 DTO도 검증하나요? | 보통 안 함. 검증은 밖에서 들어오는 값에 함. 응답은 어떤 칸을 내보낼지 정하고, 약속대로 나가는지는 REST Docs 같은 테스트로 확인 |
| DB 중복 키 에러는 어떻게 409가 되나요? | 따로 처리하지 않으면 500. 서비스에서 먼저 중복을 확인해 409를 던지고, 동시에 들어와 DB에서 걸린 경우도 409로 바꾸는 처리기를 둠 |
