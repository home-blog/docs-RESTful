## 3. API = 식당 메뉴판 (1:15)

**화면**
- 그림: 손님(클라이언트) → 주문서(요청) → 주방(서버) → 음식(응답)
- 요청 한 장 예시 (색으로 네 부분 구분)

```http
POST /api/v1/posts                ← 메서드 + 주소
Content-Type: application/json    ← 헤더
{ "title": "제주도 3박 4일" }      ← 바디
```

- 응답 예시: `201 Created` + JSON

**대사**
> API는 프로그램끼리 대화하는 창구예요. 식당으로 치면 메뉴판과 주문 시스템입니다. 손님은 주방에 들어가지 않고 주문서만 내죠.
> 앱도 서버의 데이터베이스를 직접 열지 않고, 요청을 보내서 결과를 받아요.
> 요청은 네 부분이에요. **무엇을 할지(메서드), 어디에(주소), 부가 정보(헤더), 내용물(바디).** 응답은 결과 번호(상태 코드)와 내용물이 와요.

## 4. REST = 세 줄 약속 (0:50)

**화면** (크게 세 줄)

```text
① 무엇(자원)  → URL          /posts/42
② 어떻게(행동) → HTTP 메서드  DELETE
③ 결과        → 상태 코드     204 No Content
```

**대사**
> REST는 이름은 어렵지만 내용은 세 줄이에요. **무엇은 주소로, 어떻게는 메서드로, 결과는 상태 코드로.**
> "DELETE /posts/42 → 204" 하면 "42번 글을 지웠고 잘 됐다"는 뜻이에요. 지금부터 이 세 줄을 하나씩 풀어 보겠습니다.

## 5. 자원 중심 URL (1:45)

**화면**

| ❌ | ✅ |
|---|---|
| `GET /getPosts` | `GET /posts` |
| `POST /createPost` | `POST /posts` |
| `GET /deletePost?id=42` | `DELETE /posts/42` |

규칙 4줄
- 명사, **복수형** (`/posts`)
- 소문자 + 하이픈 (`/blog-categories`)
- 관계는 슬래시, **2단계까지** (`/posts/42/comments`)
- **누구냐 → 경로 / 어떻게 보여 줄까 → 쿼리** (`/posts?sort=createdAt,desc`)

**대사**
> 첫 번째, URL에는 **명사만** 씁니다. get, create, delete 같은 동사는 메서드가 대신 말해 줘요.
> 특히 왼쪽 세 번째, **GET으로 삭제하는 API는 위험**해요. 검색 로봇이 링크를 "구경만" 해도 글이 지워질 수 있거든요.
> 그리고 기억할 한 줄. **"42번 글"처럼 누구인지는 경로에, "최신순으로, 20개씩"처럼 어떻게 보여 줄지는 물음표 뒤에** 붙입니다.

## 6. HTTP 메서드 + 멱등 (1:45)

**화면**

| 메서드 | 뜻 | 예 |
|---|---|---|
| GET | 조회 | `GET /posts/42` |
| POST | 생성 | `POST /posts` |
| PUT | 통째로 교체 | `PUT /posts/42` |
| PATCH | 일부 수정 | `PATCH /posts/42` |
| DELETE | 삭제 | `DELETE /posts/42` |

그림 두 개: 🛗 엘리베이터 버튼(멱등: PUT, DELETE) vs 🥤 자판기 버튼(멱등 아님: POST)

**대사**
> 메서드는 다섯 개만 기억하세요. 조회, 생성, 교체, 수정, 삭제.
> 헷갈리는 게 PUT과 PATCH인데요, **PUT은 서류를 통째로 갈아 끼우는 것**, **PATCH는 수정 테이프로 일부만 고치는 것**이에요. 제목만 고치려고 PUT을 쓰면 본문이 날아갈 수 있어서, 수정 기능은 보통 PATCH를 씁니다.
> 하나 더. **엘리베이터 버튼은 열 번 눌러도 한 번 와요.** 이걸 멱등이라고 하는데, PUT과 DELETE가 그래요. 반면 **POST는 자판기 버튼**이라 열 번 누르면 글이 열 개 생겨요. 그래서 "글 쓰기" 버튼은 한 번 누르면 막아 두는 거예요.

## 7. HTTP 상태 코드 (1:45)

**화면**

```text
2xx 성공       200 OK   201 Created   204 No Content
4xx 요청 잘못   400 형식   401 누구세요?   403 권한 없음   404 없음   409 충돌
5xx 서버 잘못   500 서버 오류   503 잠시 불가
```

그림: 회사 출입증 — 401 "출입증 안 찍음" / 403 "찍었지만 이 층은 못 들어감"

하단 경고: ❌ `200 OK` + `{ "success": false }`

**대사**
> 상태 코드는 택배 상자 겉에 붙은 스티커 같은 거예요. 열어 보지 않아도 결과를 알 수 있죠.
> 첫 숫자만 기억하세요. **2는 성공, 4는 요청한 쪽 잘못, 5는 서버 잘못.**
> 가장 헷갈리는 401과 403은 출입증으로 기억하세요. 401은 "누구세요? 출입증 찍고 오세요", 403은 "누군지는 알지만 이 층은 안 돼요".
> 그리고 하지 말아야 할 것 하나. **실패했는데 200을 주면** 모니터링이나 재시도 도구가 전부 성공으로 착각합니다.

## 8. 공통 응답·에러 형식 (1:15)

**화면** (에러 예시 하나만 크게)

```json
404 Not Found
{
  "title": "글을 찾을 수 없습니다",
  "status": 404,
  "detail": "42번 글이 없거나 삭제되었습니다.",
  "code": "POST_NOT_FOUND"
}
```

포인트 3개
- 응답 모양은 **팀에서 하나로** (필드 이름, 날짜 형식)
- 에러는 **표준 형식**(RFC 9457 Problem Details) + 우리 `code`
- 화면은 **문장이 아니라 code로** 판단 / 내부 오류 내용은 응답에 넣지 않기

**대사**
> API가 50개인데 에러 모양이 다 다르면, 화면 개발자는 50가지 처리를 해야 해요. 그래서 응답 모양을 하나로 통일합니다.
> 에러 형식은 다행히 **인터넷 표준**이 있어요. Spring Boot도 기본으로 지원하고요.
> 여기서 code 칸이 중요한데요, 메시지 문장은 언제든 바뀔 수 있으니 **프로그램은 이 코드를 보고** 판단하게 합니다.

## 9. 전역 예외 처리와 입력 검증 (1:30)

**화면** (왼쪽: 그림, 오른쪽: 코드 두 조각)

```text
진료실(컨트롤러)들 ──문제 발생──▶ 원무과 창구(@RestControllerAdvice) ──▶ 같은 양식의 안내
```

```java
public record CreatePostRequest(
    @NotBlank @Size(max = 100) String title,
    @NotBlank String content) {}
```

```java
@RestControllerAdvice
class GlobalExceptionHandler {
    @ExceptionHandler(ApiException.class)
    ProblemDetail handle(ApiException e) { ... }
}
```

**대사**
> 에러 처리를 API마다 따로 하면 코드가 반복되고 모양도 제각각이 돼요.
> 그래서 병원처럼 합니다. 진료실은 진료만 하고, 문제가 생기면 **원무과 창구 한 곳**에서 같은 양식으로 안내하는 거죠. Spring에서는 이 창구가 `@RestControllerAdvice`예요.
> 그리고 입력 검증. "화면에서 이미 검사하는데요?" 하실 수 있는데, API는 화면 없이도 부를 수 있어요. **공항에서 카운터가 짐을 재 줘도 보안 검색대는 절대 생략하지 않죠.** 서버 검사가 그 검색대예요.

## 10. 페이징·검색·정렬 (1:00)

**화면**

```text
GET /api/v1/posts?topic=TRAVEL&keyword=제주&sort=createdAt,desc&page=0&size=20
                  └──── 검색 ────┘ └────── 정렬 ──────┘ └─── 페이징 ──┘
```

| 방식 | 언제 |
|---|---|
| 오프셋 `?page=2&size=20` | 게시판 (1 2 3 페이지 번호) |
| 커서 `?cursor=…&size=20` | 무한 스크롤, 데이터가 아주 많을 때 |

안전장치: **size 최댓값 · 기본 정렬 · 정렬 가능한 칸 제한**

**대사**
> 글이 100만 개인데 한 번에 다 줄 수는 없겠죠. 도서관에서 "소설 코너에서, 최신순으로, 20권씩" 달라고 하듯이, 조건을 물음표 뒤에 붙여요.
> 페이지 번호가 있는 게시판은 오프셋, 인스타처럼 계속 내리는 화면은 커서 방식이 잘 맞아요.
> 그리고 `size=100만` 같은 요청에 서버가 멈추지 않게 **최댓값은 꼭** 정해 둡니다.
