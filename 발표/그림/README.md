## API와 RESTful API (슬라이드 2)

![웹·앱·관리자 페이지·다른 서비스가 같은 API를 쓰는데, API는 형식이 자유로워 제각각일 수 있으므로, REST 원칙(자원은 URL, 행동은 메서드, 결과는 상태 코드)으로 통일한 것이 RESTful API다.](00-0-API와-RESTful-API.png)

> API는 프로그램끼리 요청과 응답을 주고받는 방법입니다. 우리가 만드는 API는 웹, 모바일 앱, 관리자 페이지, 다른 서비스가 모두 같이 씁니다. 그런데 API는 형식이 정해져 있지 않아서, 같은 "42번 글 삭제"도 만든 사람마다 왼쪽처럼 제각각일 수 있습니다. 그러면 쓰는 쪽은 API마다 문서를 찾거나 물어봐야 합니다. 그래서 REST라는 원칙으로 형식을 통일합니다. 자원은 URL로, 행동은 HTTP 메서드로, 결과는 상태 코드로 표현합니다. 이렇게 만든 API가 RESTful API입니다. DELETE /api/v1/posts/42 한 줄만 봐도 42번 글을 삭제한다는 걸 알 수 있습니다. 그럼 먼저, 이런 요청을 왜 보내는지부터 보겠습니다.

## 왜 요청을 보내나 (슬라이드 3)

![화면에 보이는 데이터는 서버의 DB에 있으므로, 사용자의 동작 하나하나가 서버로 보내는 HTTP 요청 하나가 된다.](00-왜-요청을-보내나.png)

> 웹이나 앱 화면에 보이는 글, 댓글, 회원 정보는 사용자 기기가 아니라 서버의 DB에 있습니다. 그래서 화면은 데이터가 필요할 때마다 서버에 요청을 보냅니다. 첫 화면을 열면 글 목록을 조회하는 GET이, 저장 버튼을 누르면 글을 만드는 POST가 나갑니다. 사용자의 동작 하나가 HTTP 요청 하나입니다.

## 동사 URL의 문제 (슬라이드 5)

![URL에 동사를 넣으면 같은 글인데도 기능마다 주소가 늘어나고 이름도 사람마다 달라지지만, REST로 만들면 주소 하나에 메서드만 바뀌고 누가 만들어도 같은 모양이 된다.](04-0-동사-URL의-문제.png)

> 먼저 URL입니다. URL에 동사를 넣으면 두 가지 문제가 생깁니다. 첫째, 같은 42번 글인데도 getPost, updatePost, deletePost처럼 기능마다 주소가 하나씩 늘어납니다. 둘째, 이름이 사람마다 다릅니다. 같은 조회를 누구는 getPost, 누구는 fetchComment, 누구는 selectMember.do라고 짓고, 파라미터 이름도 id, no, mid로 제각각입니다. 그래서 행동은 메서드에 맡기고 URL은 명사로 자원만 가리킵니다. 그러면 /posts/42 하나에 메서드만 바꿔 조회, 수정, 삭제를 하고, 댓글은 /comments/7, 회원은 /members/3처럼 누가 만들어도 같은 모양이 됩니다.

## 동사 URL과 자원 URL (슬라이드 5)

![URL에 동사를 넣는 대신, 행동은 HTTP 메서드로 표현하고 URL은 명사로 자원만 가리킨다.](04a-동사-URL과-자원-URL.png)

> 자주 쓰는 기능을 바꿔 보면 이렇습니다. 동사는 빠지고, 같은 주소에 메서드만 달라집니다. 특히 삭제를 GET으로 만들면 안 됩니다. GET은 데이터를 바꾸지 않는 요청으로 정의되어 있어서, 검색 엔진 크롤러나 메신저의 링크 미리보기는 사용자가 누르지 않아도 GET을 보냅니다. 삭제 URL을 메신저로 보내기만 해도 글이 지워질 수 있습니다.

## 자원 중심 URL (슬라이드 5)

![URL은 명사를 계층으로 이어 붙여 자원을 가리키고, 누구인지는 경로에, 보여 주는 방식은 쿼리에 두며, 소문자와 하이픈, 버전 접두사를 쓴다.](04b-자원-중심-URL.png)

> 명사 URL은 계층으로 짭니다. 글 목록은 /posts, 42번 글은 /posts/42, 그 글의 댓글은 /posts/42/comments입니다. 중첩은 2단계까지만 둡니다. 더 깊어지면 상위 id를 모두 알아야 하니, 댓글 하나는 /comments/7처럼 끊습니다. 어떤 자원인지는 경로에, 정렬이나 개수처럼 보여 주는 방식은 물음표 뒤 쿼리에 둡니다. URL은 소문자와 하이픈으로 쓰고, 앞의 /api/v1은 버전입니다. 응답 구조를 크게 바꿔야 할 때 예전 앱이 깨지지 않도록 /api/v2를 따로 열기 위해 붙여 둡니다.

## 메서드별로 달라지는 결과 (슬라이드 6)

![같은 42번 글에 메서드만 바꾸면 결과가 달라진다. PUT은 통째로 교체해 안 보낸 본문이 사라지고, PATCH는 보낸 제목만 고친다.](05-메서드별-결과.png)

> 다음은 메서드입니다. 같은 42번 글에 메서드만 바꿔 보내면 결과가 이렇게 달라집니다. GET은 조회, POST는 생성, DELETE는 삭제입니다. 헷갈리는 건 PUT과 PATCH입니다. 둘 다 제목만 보냈는데, PUT은 자원 전체를 교체해서 안 보낸 본문이 비워질 수 있고, PATCH는 보낸 필드만 바꿉니다. 그래서 일부 수정에는 PATCH를 씁니다. 하나 더, PUT과 DELETE는 여러 번 보내도 결과가 같지만, POST는 보낼 때마다 글이 하나씩 생깁니다. 그래서 글쓰기 버튼은 한 번 누르면 막아 두고, 결제처럼 중요한 POST는 중복 요청을 막는 처리를 합니다.

## 상태 코드 네 갈래 (슬라이드 7)

![서버의 처리 결과는 2xx 성공, 3xx 리다이렉트, 4xx 클라이언트 오류, 5xx 서버 오류 네 갈래로 나뉘고, 실패를 200으로 주면 안 된다.](07-상태-코드-네-갈래.png)

> 결과는 상태 코드로 알립니다. 첫 자리로 종류가 나뉩니다. 2xx는 성공, 3xx는 리다이렉트, 4xx는 요청한 쪽 문제, 5xx는 서버 문제입니다. API에서는 주로 2xx, 4xx, 5xx를 씁니다. 하지 말아야 할 게 하나 있습니다. 실패했는데 200 OK에 success: false를 담아 보내는 방식입니다. 모니터링, 프론트엔드의 에러 처리, 자동 재시도, 캐시는 바디를 읽지 않고 상태 코드만 봅니다. 그래서 실패를 200으로 주면 장애가 나도 알림이 오지 않고, 화면에는 저장 완료가 뜹니다. 세밀한 구분이 필요하면 상태 코드는 그대로 두고, 바디에 에러 코드를 따로 담습니다. 이건 바로 다음에 보겠습니다.

## 자주 만나는 에러 상태 코드 (슬라이드 7)

![실제로 자주 보는 에러 코드는 400, 401, 403, 404, 409와 500, 502, 503, 504이며, 코드마다 먼저 확인할 곳이 다르다.](07b-자주-만나는-에러-코드.png)

> 실무에서 에러가 나면 대부분 이 아홉 개 중 하나입니다. 가장 자주 보는 건 400, 401, 404, 500입니다. 400은 값이 빠졌거나 형식이 틀린 경우, 404는 자원이 없거나 URL이 틀린 경우, 500은 서버가 처리하지 못한 예외라 서버 로그를 봐야 합니다. 헷갈리는 401과 403은 실패한 단계가 다릅니다. 401은 JWT나 세션이 없거나 만료되어 누구인지 모르는 경우, 403은 누구인지는 알지만 권한이 없는 경우입니다. 502, 503, 504는 게이트웨이 뒤의 서버에 문제가 있을 때 나옵니다.

## 공통 에러 형식 (슬라이드 8)

![API마다 다른 에러 모양을 표준 형식 하나로 통일하면, 화면은 code 하나만 보고 처리할 수 있다.](09-공통-에러-형식.png)

> 응답도 형식을 하나로 맞춥니다. 성공 응답은 단건이면 자원을 그대로, 목록이면 content와 page로 감싸서 주고, 필드 이름은 camelCase, 날짜는 ISO-8601로 통일합니다. 그럼 에러는 어떻게 보낼까요. 왼쪽처럼 API마다 에러 모양이 다르면, 프론트엔드는 API마다 에러를 꺼내는 코드를 따로 짜야 하고, 문장으로 분기했다가 백엔드가 문구를 고치면 깨집니다. 회원 API는 앞에서 말한 200 문제까지 있습니다. 그래서 오른쪽처럼 모든 API가 같은 형식으로 보냅니다. RFC 9457 표준의 type, title, status, detail에 우리 팀 에러 코드 code를 붙입니다. 프론트엔드는 에러 처리를 한 곳에만 쓰고, code로 분기하고, detail 문장은 화면에 보여 주기만 합니다. 스택 트레이스나 SQL 같은 내부 정보는 응답에 넣지 않고 서버 로그에만 남깁니다.

그림은 `발표/그림/만들기/그림-생성.py` 로 만듭니다. 글자나 위치를 바꾼 뒤 아래처럼 다시 만들면 됩니다.

```bash
python3 발표/그림/만들기/그림-생성.py 발표/그림     # SVG 다시 만들기
node 발표/그림/만들기/png-만들기.js 발표/그림          # PNG 다시 만들기 (Playwright 필요)
node 발표/그림/만들기/png-만들기.js 발표/그림/애니메이션
```
